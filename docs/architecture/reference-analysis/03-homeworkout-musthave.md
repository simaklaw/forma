# Home Workout v1.1.8 MustHave — архитектурный и продуктовый разбор

**Репозиторий:** `simaklaw/home-workout-musthave-analysis`  
**Анализируемый предмет:** Home Workout v1.1.8 MustHave, package `homeworkout.homeworkouts.noequipment`  
**Статус источников:** в рабочем дереве есть README и Markdown-карта классов; SQL, Dart, TypeScript/TSX и JSON-файлы отсутствуют. История Git содержит пять коммитов, из которых два относятся непосредственно к первичной и классовой фиксации Home Workout. Поэтому ниже отделены **зафиксированные факты** от **осторожной реконструкции по именам экранов**. Fitify-материалы и план FORMA не используются как доказательство внутренней реализации Home Workout.

## Итог

Home Workout v1.1.8 MustHave представлен в репозитории как компактное Android-приложение домашних тренировок из того же семейства, что и «Тренировки для Дома Pro». Для него зафиксированы около 1 121 классов, пакет `homeworkout.homeworkouts.noequipment`, APK примерно 19 МБ и основной продуктовый контур: главный экран, каталог/просмотр упражнений, выполнение тренировки, результат, история, HIIT-сценарии, пауза/выход, отдельная цепочка настройки сложности и экран оплаты.[1] [2]

Имеющихся материалов достаточно, чтобы уверенно описать **границы экранов и модульные зоны**, но недостаточно для доказательства маршрутизации, алгоритма тренировки, модели объектов, локального хранилища либо серверной базы. В частности, нельзя из наличия групп `model` и `data` выводить Room, SQLite, Firebase Firestore, конкретные таблицы, поля, первичные/внешние ключи, статусы или аналитические события.[2]

> **Ключевое ограничение:** репозиторий не содержит исходников Home Workout, декомпилированных классов, manifest, ресурсов или SQL-дампа для этого APK. Имена Activity и агрегированные количества классов — это карта поверхности приложения, а не контракт его внутренней модели или БД.

## Сущности тренировок и отношения

### Что подтверждено

Следующие существительные и их пользовательские поверхности подтверждены именами экранов:

| Наблюдаемый концепт | Прямое доказательство | Надёжный вывод |
|---|---|---|
| **Упражнение (`Exercise`)** | `ExerciseActivity`, `ExerciseInfoActivity`, `ExercisePreviewActivity`, `ExerciseResultActivity`, `AllExerciseActivity` | Упражнение является центральным понятием нескольких экранов: список, сведения, preview, выполнение и результат. |
| **HIIT** | `HiitListActivity`, `HiitActionIntroActivity` | В приложении есть отдельная HIIT-ветка как минимум с выбором из списка и вводом к действию. |
| **Действие (`Action`)** | `DoActionActivity`, `HiitActionIntroActivity` | Термин присутствует в UI, но его равенство упражнению, сету или шагу не доказано. |
| **Результат упражнения** | `ExerciseResultActivity`, `ExerciseResultNewActivity` | Есть экран(ы) результата, вероятно после выполнения упражнения; поля результата не известны. |
| **История** | `LWHistoryActivity` | Предусмотрен пользовательский экран истории. Нет доказательства, что он хранит записи в локальной БД, а не вычисляет/получает их иначе. |
| **Настройка сложности и feedback** | `AdjustDiff*`, включая `FeedBack` | Регулировка сложности реализована как отдельный UI-flow. Неизвестно, какие уровни/ответы существуют и меняет ли flow контент. |

### Осторожно реконструируемые связи

Ниже приведены только отношения на уровне **пользовательской логики**. Они не являются восстановленной схемой классов или БД.

```text
AllExercise / HIIT list
        │  (выбор — осторожная реконструкция)
        ▼
Exercise information / preview / instruction
        │  (старт выполнения — осторожная реконструкция)
        ▼
ExerciseActivity / ExerciseActivityNew / DoActionActivity
        ├── PauseActivity
        ├── ExitActivity
        └── ExerciseResultActivity / ExerciseResultNewActivity
                    │  (отображение в истории предполагается по продуктовому циклу)
                    ▼
              LWHistoryActivity

AdjustDiffAsk → AdjustDiffPreview → AdjustDiffFeedBack → AdjustDiffFinish
```

Самая обоснованная связь — продуктовая последовательность «каталог → упражнение → результат → история», прямо сформулированная в сравнительном README.[3] Переходы между конкретными Activity на диаграмме, выбор версии `New`/старой Activity и связь HIIT с `DoActionActivity` **не подтверждены кодом**; они показаны как навигационная гипотеза, вытекающая только из названий.

Не подтверждены для Home Workout: `Workout`, `WorkoutItem`, `WorkoutSession`, `Plan`, `PlanDay`, `FitnessPlan`, custom workout, achievement, progress metric, health integration и breathwork. Эти понятия приведены в части Fitify/FORMA того же репозитория, но переносить их в модель Home Workout без первичного исходника было бы ошибкой.[3] [5]

Можно говорить лишь о **логических пользовательских объектах**, которые должны быть представлены на экранах, но нельзя объявлять их записями БД.

## Пошаговый UX workout player

Ниже не выдается за снятый сценарий APK. Это минимальный маршрут, который можно аккуратно восстановить из набора экранов и описания базового продуктового цикла.[2] [3]

1. **Точка входа.** Пользователь начинает в `MainActivity`. Это подтверждённый главный экран, но его табы, кнопки и стартовый маршрут не известны.
2. **Выбор контента.** Для обычной ветки доступен `AllExerciseActivity`; для HIIT есть `HiitListActivity`. Можно осторожно предположить, что это поверхности выбора упражнения или HIIT-активности, поскольку одна явно названа списком всех упражнений, а другая — списком HIIT.
3. **Подготовка.** Выбранное упражнение может быть представлено в `ExerciseInfoActivity`, `ExercisePreviewActivity` и/или `InstructionActivity`; в HIIT-ветке есть `HiitActionIntroActivity`. Нельзя определить, все ли эти экраны обязательны, их порядок или whether preview относится к одному упражнению либо комплексу.
4. **Выполнение.** Выполнение связано с `ExerciseActivity`, `ExerciseActivityNew` и/или `DoActionActivity`. Наличие старой и `New`-версии говорит о нескольких UI-вариантах, но не раскрывает условие выбора.
5. **Временное прерывание.** `PauseActivity` даёт отдельную поверхность для паузы. Из названия не следует, сохраняется ли таймер, разрешён ли skip или восстанавливается ли сессия после перезапуска.
6. **Досрочный выход.** `ExitActivity` показывает, что ранний выход вынесен в самостоятельный сценарий. Причины выхода, подтверждение и последствия для истории не раскрыты.
7. **Завершение.** `ExerciseResultActivity` и `ExerciseResultNewActivity` представляют результат. Именно наличие отдельного результата подтверждено; конкретные сводные метрики и CTA не известны.
8. **Постфактум.** `LWHistoryActivity` является поверхностью истории; сравнительное описание фиксирует общий цикл с переходом к истории. Нельзя утверждать автоматическое сохранение, фильтрацию, календарь или возможность редактирования записи.
9. **Адаптация сложности.** Отдельная цепочка `Ask → Preview → FeedBack → Finish` предполагает пошаговую настройку сложности. Она может быть отдельной от завершения упражнения; её триггер и результат не подтверждены.

## Сильные стороны, наблюдаемые в артефактах

1. **Полный базовый пользовательский контур.** Набор `AllExerciseActivity`, семейство `Exercise*`, семейство `ExerciseResult*` и `LWHistoryActivity`, а также явное описание цикла в comparison-документе, указывает на охват выбора, выполнения, результата и ретроспективы.[2] [3]
2. **Явная адаптация сложности.** Четырёхшаговая серия `AdjustDiff*` выделяет настройку сложности в самостоятельный сценарий, а не оставляет её неявной настройкой.[2]
3. **Разделение контента и исполнения.** Информация, preview, инструкция и непосредственное выполнение упражнений имеют разные экранные границы. Это создаёт возможность не перегружать player справочной информацией.[2]
4. **Специализированная HIIT-ветка.** Отдельные список и вводный action-экран HIIT демонстрируют, что интервальный сценарий рассматривается отдельно от общего каталога.[2]
5. **Выделенные контрольные точки сессии.** Отдельные Activity для pause, exit и result делают важные пользовательские развилки видимыми в карте классов.[2]
6. **Отделённые монетизация и рекламная зона.** Наличие `PayActivity` и пакета `ads` показывает, что коммерческая функциональность не растворена только в экранах упражнений, хотя реальная степень изоляции не доказана.[2]

## Риски и пробелы

1. **Критический пробел в доказательствах реализации.** Карта классов не содержит методов, ресурсов, интентов, state management, тестов и runtime-данных. Любая точная навигация, модель тренировки или алгоритм сложности останутся догадкой до появления декомпиляции/исходников Home Workout.
2. **БД нельзя проектировать «по названиям».** `data` и `model` в агрегированной статистике не дают оснований заявлять SQLite/Room/Firebase, таблицы, ключи или схему истории. Даже существование сохранённых результатов не подтверждено, несмотря на экран истории.[2]
3. **Дублирующиеся Activity могут отражать переходный долг.** Пары `ExerciseActivity`/`ExerciseActivityNew` и `ExerciseResultActivity`/`ExerciseResultNewActivity` указывают на несколько поколений экранов. Условие выбора, совместимость результата и миграция UI не известны; это риск неоднородного flow, но не доказательство дефекта.[2]
4. **Широкая UI-поверхность усложняет проверку.** Примерно 229 fragment-классов, 72 view-класса и 33 dialog-класса означают большую заявленную презентационную область. Без исходников неизвестны её связность, качество и покрытие тестами.[2]
5. **Монетизация и реклама требуют отдельной проверки UX.** `PayActivity` и около 52 классов `ads` подтверждены, но не известно, где пользователь встречает paywall/рекламу и влияют ли они на тренировку. Нельзя делать вывод ни о навязчивости, ни о ценовой модели.[2]
6. **Разрешения и внешний жизненный цикл не раскрыты.** `MediaPermissionActivity` есть в карте, но manifest Home Workout отсутствует. Нельзя определить реальные Android-permissions, работу в фоне, поведение на блокировке экрана и восстановление сессии.
7. **Историческая технологическая запись требует верификации.** Kotlin, Lottie, Firebase, Play Services Fitness, Billing и Ads указаны только в раннем README из Git history. До появления исходных артефактов это нельзя использовать для списка фактических SDK, политики данных или интеграционной архитектуры.[4]

## История репозитория и влияние на достоверность

Git history показывает краткую аналитическую последовательность в один день: initial commit, инициализация анализа Home Workout, добавление class map, обновление README, затем добавление Fitify-материалов и сравнительного документа.[4] [6] На момент первого шага статусы UI/UX и бизнес-логики были «ожидает»; позднейший README обозначил их как выполненные через «Fitify + первый APK в сравнении», но самостоятельного подробного Home Workout UI/UX-документа в допустимых форматах не появилось.[1] [4]

Это объясняет асимметрию данных: для Home Workout репозиторий хранит компактную карту экранов, тогда как детализация Fitify не может автоматически служить доказательством о Home Workout. Для последующей технической проверки требуются, минимум, manifest и декомпилированный код/ресурсы Home Workout либо данные runtime-наблюдения, сохранённые в разрешённом формате.
